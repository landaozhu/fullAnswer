# 高性能渲染十万条数据

【一句话】**卡的是主线程和 DOM 数量。** 一次 `for` 插十万节点会占死主线程；时间分片把插入切开，虚拟列表让同一时刻只有可视区那几十个 DOM。优先虚拟列表，时间分片是「必须真的插很多节点」时的退路。

直接全量插 DOM 会怎样：这一轮 JS 可能跑几百毫秒，浏览器画不了下一帧，点击、滚动也进不来。

| 方案 | 解决什么 | 不解决什么 |
|---|---|---|
| 时间分片 | 插入别一次做完，主线程能喘口气 | 最终还是十万个 DOM，内存和布局仍贵 |
| 虚拟列表 | 同一时刻只有可视区 + 缓冲那几十个节点 | 不管接口怎么拉数据 |
| 分页 / 懒加载 | 数据还在服务器，别一次拉完 | 不是渲染优化本身 |

数据还在接口 → 分页。数据已在内存、列表很长 → **虚拟列表**。必须插大量真实节点、又不能一次卡死 → 时间分片。

---

## 时间分片

把主线程上一次做不完的重活按帧切开。每切一小段就把控制权还给浏览器：可以画、可以响应操作。

常用 `requestAnimationFrame`（跟帧对齐，适合往页面上插节点）。也可以 `MessageChannel` / `setTimeout` 让出事件循环。`requestIdleCallback` 是空闲再干，Safari 支持差，提一句即可。

```js
let i = 0
function tick() {
  const end = Math.min(i + 200, list.length)
  while (i < end) {
    container.appendChild(renderItem(list[i]))
    i++
  }
  if (i < list.length) requestAnimationFrame(tick)
}
requestAnimationFrame(tick)
```

不是 HTTP 分片，也不是并发上传下载。切的是 **主线程上的 JS / 插 DOM**，不是网络。

和 React Fiber 的「时间分片」是同一类思路（大任务可中断、让路），但本题说的是自己分批插节点；Fiber 切的是调和过程，而且没 commit 前不会把半成品画到页面上。

## 虚拟列表

只渲染当前看得见的那几行。滚动条高度靠一个垫高容器撑出来，数据可以全在内存。

1. 外层固定高度 + `overflow: auto`，监听 `scroll`
2. 内层高度 = `list.length * itemHeight`，保证滚动条能滚十万行
3. `startIndex = floor(scrollTop / itemHeight)`，再加可视条数和上下缓冲（overscan）
4. 只 `slice` 这一段去渲染，用 `translateY` 或绝对定位挪到正确位置
5. 滚动时同一批 DOM 换内容和位置，不是每滚一次去插新节点

可视区 20 行，同一时刻 DOM 大约是 **20 + 上下缓冲**，不是精确 20，更不是十万。

变高列表不能直接 `scrollTop / 固定高度`，要预估高度或测完缓存，按前缀和算 start/end。手写面试一般先答定高。

更完整的伪代码见 `interview/优化/虚拟滚动.md`。

## 追问

- **可视区 20 行，DOM 几个？** 20 + overscan。滚动条靠垫高，不是靠真有十万个节点。
- **时间分片还管接口吗？** 不管。数据没回来用分页 / `IntersectionObserver`。
- **为什么不只用时间分片？** 卡顿能缓解，十万 DOM 的内存、回流还在；虚拟列表从根上少节点。
- **数据一定要先全下载吗？** 不必。虚拟列表管 DOM；数据可以分页，也可以全在内存。
- **和 Fiber 时间分片？** 都是切开重活、别占死主线程。十万条这题答分批插 DOM；Fiber 答 render 可中断、commit 不可中断。
